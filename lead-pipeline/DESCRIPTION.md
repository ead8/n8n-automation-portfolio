# Lead-to-Meeting Pipeline: n8n Workflow Design

**Test task for Shreim, AI Workflow Automation Specialist role**
Ebisa Dugo

## What this is

This document describes an n8n workflow that takes a website lead from form submission to a booked calendar meeting, with a reminder the day before. The pipeline has four steps:

1. A website lead comes in.
2. The lead gets an instant WhatsApp reply.
3. The lead books a meeting on a calendar.
4. The lead gets a reminder the day before the meeting.

For each step I describe what the workflow does, what can fail, and what the workflow does when it fails. The actual importable n8n workflow files are attached with this document, along with the database schema and a diagram. Credentials in the workflow files are placeholders.

## Design principles

Five rules shaped the whole design:

- **Idempotency first.** Every external event carries a key, and the workflow checks it before doing anything twice. A lead can submit the form three times and still gets one WhatsApp message and one meeting.
- **Code owns state, the model only drafts.** An LLM helps read the lead's replies and extract a preferred time. It never books, cancels, or sends on its own. Plain code validates every value before it touches the calendar or the database.
- **Templates where WhatsApp requires them.** The lead has not messaged us first, so the opening message and the reminder go out as pre-approved WhatsApp templates. The form captures WhatsApp opt-in at submission.
- **Every failure has a next step.** A failure is never just logged. It retries, falls back to another channel, or lands in a dead-letter table with an alert to a human.
- **Everything is logged against the lead.** Each run writes events to Postgres against the lead ID, so any lead's full history can be replayed when something looks wrong.

## The system at a glance

Three workflows plus one shared error handler, all backed by one Postgres database:

- **Lead Pipeline: Intake + WhatsApp Welcome.** Form webhook, validation, dedupe, lead creation, the instant WhatsApp template.
- **Lead Pipeline: WhatsApp Replies + Calendar Booking.** Inbound WhatsApp webhook, intent and slot extraction, availability check, booking with read-back, confirmation.
- **Lead Pipeline: Day-Before Reminder Sweep.** Hourly schedule trigger that finds meetings about 24 hours out, verifies they still exist, and sends the reminder template.
- **Lead Pipeline: Global Error Handler.** An n8n error workflow. Any failed execution in the three workflows above lands here, gets logged, and posts an alert to an ops Slack channel.

## Step 1: Website lead comes in

A form on the website posts to an n8n webhook. The payload carries name, email, phone, the service the lead wants, and a submission ID generated by the form.

The workflow validates and normalizes first: required fields present, email format checked, phone converted to E.164 format. It builds an idempotency key from the submission ID, or from a hash of phone plus email when the form does not send one. Then it checks Postgres for an existing lead with that key or phone number. New leads are inserted with status NEW and a `lead.created` event.

**What can fail, and what happens:**

- **Duplicate submissions** (double click, browser retry, form resubmission). The idempotency check catches them. The workflow returns the existing lead state and stops. No second WhatsApp message, no second record.
- **Malformed payload** (missing phone, bad email). Validation rejects it with a 400 response before any side effect. The rejection is logged so form bugs are visible.
- **Database down.** The insert fails and the error workflow fires: the failure is logged and ops gets a Slack alert with the execution link. The form gets a 500, so the website can show a "try again" message instead of pretending the lead was captured.
- **Webhook floods or spam.** Validation plus the dedupe check blunt most of it. In production I would add a rate limit at the reverse proxy and a honeypot field on the form.

## Step 2: Instant WhatsApp reply

Seconds after the lead is created, the workflow sends a pre-approved WhatsApp template through the WhatsApp Business Cloud API. The template greets the lead by name, confirms we received their request, and carries a quick-reply button: "Book a call". The send uses the node's built-in retry: 3 attempts with backoff, because Meta's API has transient 5xx errors like any other API. On success the workflow stores the WhatsApp message ID on the lead and sets status CONTACTED.

A template is not optional here. WhatsApp only allows free-form messages inside a 24-hour window after the lead messages us. The lead has not messaged us, so the first contact must be a template, and the form's opt-in checkbox is what makes it compliant.

**What can fail, and what happens:**

- **The number is not on WhatsApp, or is invalid.** The API returns a 4xx. Retrying is pointless for a 4xx, so the workflow stops retrying, marks the lead WHATSAPP_FAILED, and falls back to email: the lead gets the same greeting and a booking link by email instead. Sales sees the lead either way.
- **Meta API outage or rate limiting (5xx, 429).** The retry with backoff absorbs short blips. If all attempts fail, the step writes the lead to a dead-letter table with the full payload and alerts ops on Slack. A human can resend from the dead-letter queue once Meta recovers. The lead record is never lost.
- **Template rejected or paused by Meta.** This shows up as a send error with a template error code. The error handler flags it separately from ordinary failures, because the fix is in the Meta template console, not in n8n. In production the template status gets checked on a schedule so a paused template is caught before leads hit it.
- **Token expired.** Meta access tokens expire. The send fails with an auth error, ops is alerted, and sends queue to the dead-letter table until the token is rotated. Nothing fails silently.

## Step 3: Calendar booking

When the lead taps "Book a call" or replies to the WhatsApp message, Meta calls the inbound webhook of the second workflow. The workflow verifies the Meta signature (HMAC SHA-256 over the raw body), parses the message, and loads the lead by phone number.

If the lead names a time ("Tuesday at 10 works"), an LLM extracts the intent and the proposed slot as structured JSON. This is the only place a model touches the flow, and its output is treated as a suggestion: a Code node validates the slot (it parses, it is in the future, it falls in business hours in the lead's timezone). The workflow then checks Google Calendar free/busy for that slot.

- If the slot is free, the workflow creates the event with the lead as attendee, then **reads the event back**. The read-back is the double-booking guard: two leads racing for the same slot, or a calendar that accepted a write it should not have, get caught here. Only after a matching read-back does the lead become BOOKED, with the event ID and start time stored.
- If the slot is taken, the workflow probes the next business slots, finds three that are free, and offers them as WhatsApp reply buttons. The lead taps one and the same check-create-verify path runs.

Confirmation goes out on WhatsApp (the lead has now messaged us, so the 24-hour window is open and free-form text is fine) plus an email with the calendar invite.

**What can fail, and what happens:**

- **The lead's message is vague** ("sometime next week?"). The extractor returns no slot. The workflow does not guess: it replies with the booking link and the three nearest open slots instead.
- **The model invents a time or misreads the day.** The validator rejects past or out-of-hours slots before the calendar is touched. The model proposes, code disposes.
- **Double-booking race.** The create-then-read-back pattern detects a lost race. The workflow deletes its event, apologizes, and offers alternatives. No lead ever sees a confirmed meeting that is not really on the calendar.
- **Google Calendar outage.** Free/busy and create calls retry twice. If Google is still down, the lead gets a WhatsApp message saying booking is having trouble, with a direct booking link as the fallback, and ops is alerted. The lead's requested slot is saved on the record so sales can book it manually.
- **Timezone confusion.** The form captures the lead's timezone, all times are stored in UTC, and every message renders the time in the lead's timezone. Most "the meeting moved" bugs are timezone bugs; storing one canonical UTC value removes the class.
- **The lead replies CANCEL or taps reschedule.** Button payloads are handled before the LLM path: cancel sets status CANCELLED and deletes the event; reschedule deletes the event and restarts the slot offer.

## Step 4: Day-before reminder

A separate workflow runs every hour. It selects leads with status BOOKED, `reminder_sent = false`, and a meeting start between 23 and 25 hours from now. The two-hour window plus the hourly run means a meeting is picked up exactly once, and the `reminder_sent` flag makes the send idempotent even if the sweep overlaps with itself.

Before sending anything, the sweep re-reads the calendar event. Meetings get cancelled outside the workflow (someone deletes the event in Google Calendar), and reminding a lead about a dead meeting is worse than no reminder. If the event is gone, the lead is marked CANCELLED and sales is notified on Slack. If the event exists, the workflow sends the reminder template with Confirm and Reschedule buttons and sets `reminder_sent = true`, status REMINDED. It is a template again, because by now the 24-hour window from the lead's last message may be closed.

**What can fail, and what happens:**

- **The sweep itself is down for a few hours** (n8n restart, deployment). A second query catches up: meetings 2 to 23 hours out with `reminder_sent = false` still get a reminder, flagged late, and the sweep posts a summary to Slack so the team knows reminders went out late.
- **The meeting was rescheduled in the calendar.** The stored start time no longer matches the event. The sweep trusts the calendar, not its own copy: it updates the stored start time from the event and re-times the reminder from the real value.
- **The reminder send fails.** Same pattern as step 2: retries, then dead-letter plus ops alert, and an email reminder as the fallback channel.
- **The lead taps Reschedule on the reminder.** The booking workflow handles it: old event deleted, new slot offered, `reminder_sent` reset to false so the new meeting gets its own reminder.

## Error handling summary

| Step | Main failures | Workflow response |
|---|---|---|
| Lead intake | Duplicates, bad payloads, DB down | Idempotency key check, 400 on invalid input, error workflow alert |
| WhatsApp welcome | Number not on WhatsApp, Meta outage, template paused, token expired | No retry on 4xx, email fallback; backoff retries on 5xx, dead-letter plus Slack alert |
| Booking | Vague or invented slots, double-booking race, Google outage, timezone errors | Code validates all model output, create then read-back, alternatives offered, booking link fallback, UTC storage |
| Reminder | Cancelled meetings, sweep downtime, send failures | Event re-verified before sending, catch-up query, fallback email, status kept honest |

Cross-cutting: any node failure in any of the three workflows also triggers the global error workflow, which writes the failure to a `pipeline_errors` table and posts workflow name, node, and execution link to the ops Slack channel. Retries are set per node, not globally: 3 attempts for WhatsApp sends, 2 for calendar calls, none for validation failures.

## Data model

One `leads` table carries the state machine: NEW, CONTACTED, BOOKED, REMINDED, plus CANCELLED, WHATSAPP_FAILED, and COMPLETED. Key fields: `idempotency_key` (unique), `phone`, `email`, `event_id`, `meeting_start` (UTC), `timezone`, `reminder_sent`, `last_error`. Two support tables: `pipeline_events` (every step transition, against the lead ID) and `dead_letter` (failed steps with full payloads, for human resend). The schema is in the attached `db/schema.sql`.

## How I would test this before real leads touch it

Same approach I use on my own builds: separate test credentials and a test WhatsApp number, so test runs can never message a real lead. Then manual executions replaying recorded payloads, including the ugly ones: duplicate form posts, a phone number with no WhatsApp, a slot that is already taken, a cancelled event before the reminder. Then a dry-run mode that logs what it would send without sending, a pilot on my own number, and only then real traffic.
